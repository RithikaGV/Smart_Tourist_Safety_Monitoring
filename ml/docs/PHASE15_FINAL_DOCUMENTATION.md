# Nilgiris Tourist Safety — AI/ML Module Documentation

**Scope:** `ml/` folder only. Frontend and Backend are built by other
teammates. Geographic scope: Nilgiris district, Tamil Nadu, India, only.

---

## Project Summary

This module is an AI Safety Engine made of 6 independent parts, each
solving a different piece of the tourist-safety problem:

| # | Module | Type of AI | Powers |
|---|---|---|---|
| 1 | Risk Prediction | Supervised classification | Destination Safety Score, Danger Alerts |
| 2 | Safety Score | Weighted formula | "Overall Safety: X/100" |
| 3 | Suspicious Movement | Unsupervised anomaly detection | Admin: Suspicious Movement Alerts |
| 4 | Tourist Behaviour Analysis | Unsupervised clustering | Admin: Behaviour view |
| 5 | Smart Deviation Alert | Rule-based (no ML) | "You are off your route" |
| 6 | Pattern Detection | Unsupervised anomaly detection (sequence-aware) | Admin: Pattern Detection, Risk Heatmap |

**The single most important thing to know about this entire project:**
almost all "ground truth" used to train and evaluate these models is
**synthetic** — generated by documented rules we wrote ourselves, because
no real incident/crime/tourist-movement dataset exists publicly for this
district. Every result in this document should be read as **"the
pipeline works correctly and learns the intended pattern,"** not
**"this is validated against real-world danger."** This distinction is
repeated in each module section below because it applies differently to
each one.

## Module 1 — Risk Prediction

**Objective:** classify a location as Safe or Dangerous.

**Dataset:** `final_features.csv` (60 real Nilgiris places) merged with
weather (partially real, partially placeholder pending Colab pipeline),
crime score (synthetic), crowd density (synthetic), and emergency-service
distance (partially real, pending Colab pipeline).

**Features used:** rainfall stats, heavy-rain-day count, temperature,
distance to hospital/police, crowd density, crime score, restricted-zone
flag, cluster, place type.

**Model used:** XGBoost (primary), Random Forest (comparison).

**Why this model:** tabular, mixed-type data (numeric + categorical) is
exactly XGBoost's strength; it also gives feature importances and is
SHAP-compatible for explainability (Module 12 requirement).

**Results (5-fold cross-validated, tuned hyperparameters):**
- Accuracy: 0.917 (+/- 0.091)
- Precision (Dangerous): 0.850 (+/- 0.300)
- Recall (Dangerous): 0.800 (+/- 0.245)
- F1 (Dangerous): 0.747 (+/- 0.229)

**Evaluation notes:** only 9 of 60 places are labeled "Dangerous" — a
small sample, reflected in the wide +/- swings above. Labels came from a
documented weighted rule (`generate_risk_labels.py`), not real incidents.
Weather features currently show 0.000 importance because real weather
data isn't merged in yet.

**Explainability (SHAP):** implemented in `explain_risk_predictions.py`.
One real finding from this: some waterfall locations were flagged
Dangerous mainly due to `type: waterfall` rather than crime/weather/
restricted status — likely an artifact of the small Dangerous sample,
flagged here rather than hidden.

**API:**
```
POST /predict-risk
in:  { crime_score, heavy_rain_days_count, restricted, distance_to_hospital_km,
       crowd_density_avg, cluster, type, ... }
out: { "prediction": "Safe" | "Dangerous", "confidence": 0.0-1.0 }
```

**Limitations:** small Dangerous-class sample; synthetic labels; weather
signal not yet active; a real label-encoding bug was found and fixed
during testing (see Phase 14 notes) — worth double-checking encoding
consistency any time this model is retrained.

## Module 2 — Safety Score

**Objective:** produce a 0–100 safety score per place (richer than binary
Safe/Dangerous).

**Dataset:** same `final_features.csv` as Module 1.

**Features used:** crime score (25% weight), heavy-rain days (20%),
restricted-zone status (20%), distance to hospital (20%), isolation —
low crowd × distance from help (15%).

**Model used:** weighted formula (v1) — deliberately NOT a trained model.

**Why this model:** no real "true" safety score exists anywhere to train
a regressor against. A transparent, documented formula means every score
can be explained exactly ("why did this place score 40?"), which matters
more for a safety app than marginal accuracy gains from a black box. A
v2 regressor stub exists (`train_safety_score_v2.py`) but is explicitly
NOT recommended for use — it can only ever approximate the v1 formula
it was trained on, so it adds no independent value yet.

**Results:** score range 35.2–73.7 across 60 places, average 65.5. All 4
restricted zones correctly scored lowest (35.2–41.0).

**Evaluation:** no accuracy/precision applies to a formula. Validated by
inspection instead — restricted/high-risk places consistently ranked
lowest, which matches expectations.

**API:**
```
POST /safety-score
in:  { crime_score, heavy_rain_days_count, restricted, distance_to_hospital_km, crowd_density_avg }
out: { "safety_score": 0-100, "risk_percentage": 0-100 }
```

**Limitations:** weights (25/20/20/20/15) are expert-assigned, not
learned or calibrated against real outcomes. Distance-to-hospital still
partially placeholder pending Colab data.

## Module 3 — Suspicious Movement Detection

**Objective:** flag tourists whose overall movement statistics look
unusual (e.g., repeated restricted-zone entries, excessive stopping).

**Dataset:** `tourist_behaviour_features.csv` — 1,000 synthetic tourists,
aggregated from 13,553 simulated visit events built on the real 60-place
graph.

**Features used:** visit count, unique clusters visited, restricted-visit
count/ratio, average dwell time, total distance, average hop distance,
revisit ratio.

**Model used:** Isolation Forest.

**Why this model:** no labeled "this tourist was suspicious" data exists
in the real world, so this has to be unsupervised. Isolation Forest
directly models "how easy is this point to isolate from the rest,"
which matches the intuition of anomaly detection well and scales better
than distance-based methods.

**Results:** flagged 100 of 1,000 tourists (10%).

**Evaluation (against injected synthetic ground truth, not real data):**
- Capture rate: 67.7% (44 of 65 synthetically-marked suspicious tourists caught)
- Precision-like: 44.0% (of everyone flagged, how many were really marked suspicious)
- Lift over random chance: 6.8x

**API:**
```
POST /detect-anomaly
in:  { n_visits, n_unique_clusters, n_restricted_visits, restricted_ratio,
       avg_dwell_minutes, total_distance_km, avg_distance_per_hop_km, revisit_ratio }
out: { "is_suspicious": true/false, "anomaly_score": float }
```

**Limitations:** `contamination=0.10` (assumed suspicious rate) is a
guessed parameter, not measured. Evaluated only against our own synthetic
rule, so real-world performance is unknown.

## Module 4 — Tourist Behaviour Analysis

**Objective:** group tourists by movement pattern for the Admin dashboard
(normal clusters vs. outliers).

**Dataset:** same `tourist_behaviour_features.csv` as Module 3.

**Model used:** DBSCAN.

**Why this model:** DBSCAN doesn't require specifying the number of
clusters upfront (unlike k-means) and naturally separates "dense normal
groups" from "sparse outliers" — a good match for "most tourists follow
similar patterns, a few don't."

**Results:** found 4 normal-behaviour clusters, 177 outliers (17.7%).

**Evaluation (same synthetic-ground-truth caveat as Module 3):**
- Capture rate: 70.8%
- Precision-like: 26.0%
- Lift over random chance: 4.0x

**Known technical limitation:** scikit-learn's DBSCAN has no native
`.predict()` for new, unseen tourists. Worked around via
`classify_new_point()` — measures distance from a new tourist to the
nearest saved "core point" from training; within `eps` = same cluster,
too far = outlier. This is a standard, documented workaround, not a bug.

**API:** not currently wrapped in `main.py` (admin-dashboard batch use
case, not necessarily live per-request — see Phase 0 notes). The
`classify_new_point()` function in `train_behaviour_dbscan.py` is ready
to be wrapped the same way as the other modules if live scoring is
needed later.

**Limitations:** eps/min_samples (1.2, 8) were chosen by inspection, not
a principled tuning process (e.g. a k-distance elbow plot). Lower
precision than Modules 3 and 6 — more false alarms per real detection.

## Module 5 — Smart Deviation Alert

**Objective:** detect when a tourist has strayed from their planned route.

**Model used:** none — pure geometry (Haversine distance + threshold),
per the Phase 0 decision that this is more reliable as a rule than a
trained model.

**How it works:** planned route (waypoints) is densely sampled into a
path every 50m; live GPS position is compared to the nearest point on
that path; alert fires if the distance exceeds the threshold (default
500m — flagged as still needing product/team confirmation, not a final
value).

**Results (self-test, real Nilgiris coordinates):** on-route tourist:
29m, no alert. Borderline tourist: 586m, alert fires correctly.
Far-off tourist (near Avalanche): 13.78km, alert fires.

**Evaluation:** correctness tested directly (deterministic, not
probabilistic) — this is the one module with a genuinely provable
right/wrong answer, unlike the ML-based modules.

**API:**
```
POST /detect-deviation
in:  { planned_route: [[lat,lon], ...], current_location: [lat,lon], threshold_km }
out: { "distance_from_route_km": float, "is_deviated": bool, "nearest_route_point": {...} }
```

**Limitations:** route is approximated as straight lines between
waypoints, not real road geometry — can slightly overstate deviation
right after a sharp mountain-road bend. A production version should snap
to real road paths (e.g. via OSRM).

## Module 6 — Pattern Detection

**Objective:** detect *repeating sequence* patterns for the Admin
dashboard — specifically the "Forest → Restricted → Forest → Restricted"
type of pattern described in the original plan, which is different from
Module 3's aggregate-stats approach.

**Dataset:** `tourist_pattern_features.csv` — same 1,000 tourists, but
with sequence-aware features instead of aggregate stats.

**Features used:** restricted-zone entry count, alternation count/ratio
(back-and-forth switching), most-common-bigram frequency, unique-bigram
ratio (how repetitive the place-to-place transitions are).

**Model used:** Isolation Forest (per Phase 0: "initially Isolation
Forest, later LSTM" — LSTM noted as a stretch goal, not attempted here,
since the current data volume doesn't obviously justify that complexity
yet).

**Why this model + these features:** same anomaly-detection reasoning as
Module 3, but with features specifically designed to catch *order*, not
just totals — this directly targets the "repeated loop" pattern from the
original spec rather than inferring it indirectly.

**Results:** flagged 76 of 1,000 tourists (7.6%) — fewer than Modules 3/4.

**Evaluation (same synthetic caveat):**
- Capture rate: 66.2%
- Precision-like: 56.6% — the best precision of all three unsupervised modules
- Lift over random chance: 8.7x — the best of the three

**Cross-module finding:** as features got more targeted (DBSCAN's raw
stats → Isolation Forest's better stats → Pattern Detection's
sequence-awareness), false alarms dropped substantially (177 → 100 → 76)
while capture rate stayed roughly flat (~67-71%). This is a genuine,
useful finding: feature design mattered more than swapping algorithms.

**API:**
```
POST /pattern-detection
in:  { n_visits, restricted_entries, alternation_count, alternation_ratio,
       most_common_bigram_freq, unique_bigram_ratio }
out: { "is_flagged_pattern": bool, "anomaly_score": float }
```

**Limitations:** `contamination=0.08` is a guessed parameter. LSTM
upgrade path noted but not built — would need substantially more
sequential data to justify.

## Overall Known Gaps (tracked honestly, not hidden)

1. **Real data not fully merged in.** Weather, hospital/police distance,
   and restricted-zone polygon boundaries all have working fetch scripts
   (`fetch_weather_data.py`, `fetch_emergency_services.py`,
   `fetch_restricted_zones.py`), but need to be run via Google Colab
   (this sandbox's network doesn't reach the required external APIs) and
   merged in via `pipeline_phase2_to_4.py` before results reflect real
   conditions rather than placeholders.
2. **Every "ground truth" label is synthetic**, generated by documented
   rules, not observed incidents. This is disclosed in every module
   section above and should be disclosed again anywhere these results
   are presented.
3. **Small Dangerous-class sample** for Risk Prediction (9 of 60 places) —
   workable for a prototype, not statistically robust.
4. **Unsupervised modules have real false-positive rates** (roughly
   44–57% precision at best) — meaningful, but would need a human
   review step in any real deployment, not fully automated action.
5. **DBSCAN's new-point classification is a workaround**, not native
   functionality — documented, tested, but worth knowing if debugging
   unexpected behaviour later.

## What's been properly tested (Phase 14)
All 5 API endpoints (`/predict-risk`, `/safety-score`, `/detect-deviation`,
`/detect-anomaly`, `/pattern-detection`) have passing automated tests
(`tests/test_api.py`, 13 tests, all passing) covering: safe/dangerous
places, on-route/off-route tourists, normal/suspicious movement, and
input validation. One real bug (a model/API encoding mismatch) was found
and fixed specifically because of this testing — a good example of why
this phase matters, not a formality.
